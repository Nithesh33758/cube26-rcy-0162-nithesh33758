PROJECT PROGRESS - RECOVERY MANAGER
LAST UPDATED:
2026-09-29

CURRENT PHASE:
Contract-based charge and reimbursement ingestion implemented; evidence/policy integration remains pending

CURRENT STATUS:
The backend accepts both the legacy 12-column charge ledger and normalized charge CSVs from recovery-data-contract.md. It has a separate reimbursement CSV import endpoint and conservatively suppresses duplicate claims when an exact order/SKU/currency reimbursement covers the charge after cancellation netting. A Gemini REST provider is integrated under backend/src/main/java/.../ai and makes one call per unit when GEMINI_API_KEY is configured. Without the key, evidence, or non-empty supplied rules, it safely returns INSUFFICIENT_EVIDENCE. The official evidence-contract.md and authoritative Amazon policy data remain unavailable, so live Gemini use and real-world decision quality are not verified. MySQL is retained by user choice; application tenant scoping is in place, but MySQL cannot satisfy RULES.md's database-enforced RLS requirement. See SESSION_HANDOFF.txt for setup and limitations.

============================================================
1. PROJECT PURPOSE
============================================================
Recovery Manager is intended to analyze ecommerce fee and reimbursement charges against relevant upstream operational evidence and applicable authoritative requirements. It should produce one decision per charge:

CLAIM
REJECT
UNCERTAIN

UNCERTAIN is a first-class decision for missing, insufficient, or contradictory evidence and should be routed for human review. The current UI models these concepts, but does not yet perform the real recovery analysis.

3. CURRENT FRONTEND WORKFLOW
============================================================
Upload CSV
  -> File Selected
  -> Validate expected ledger header and show metadata
  -> User explicitly clicks Start Analysis
  -> Processing screen
  -> Results
  -> Charge Investigation

This navigation is implemented. CSV selection does NOT automatically start analysis. The Start Analysis action alone changes the app state to PROCESSING. Invalid headers keep the user at file confirmation and disable Start Analysis.

Limit: validation currently inspects the header and counts non-empty lines. Uploaded record values are not mapped to Charge objects. App.tsx initializes charges from generateFullDataset() regardless of the selected file. ProcessingPipeline.tsx animates fixed steps and fixed counts, then transitions to the mock results.

============================================================

line_id

Additional headers are allowed. The upload validator checks the first CSV line, trims parsed header text, requires all 12 names, and rejects non-CSV files or files over 25 MiB. It reads the uploaded file in the browser to count non-empty data lines; it does not parse row values or perform robust quoted-field parsing for the full dataset.

Schema note: The supplied handoff template instead listed "Line ID", "Report Type", "Unit Id", "org id", "Quantity", "Ammount", etc. Do not change the current implementation to those names without checking the official contract and fixture. Current data/sample_input.csv and recovery-manager/src/types.ts agree on snake_case and amount_usd.

9. INTENDED BACKEND ARCHITECTURE
============================================================
PLANNED flow:

CSV
  -> Parse / Validate
  -> Match Unit Id (and org_id tenancy)
  -> Retrieve Relevant Evidence
  -> Retrieve Applicable Requirements from authoritative sources
  -> AI Reasoning
  -> CLAIM / REJECT / UNCERTAIN decision per charge
  -> Save result with evidence/rule traceability
  -> Route UNCERTAIN and other review-required cases
  -> Dashboard / Results

The AI must not be trained on the database. The backend should retrieve the necessary records and send only the relevant charge(s), evidence, and requirements to the model. Preserve tenant isolation and evidence references. Do not silently discard input when a model/dependency fails; save a pending/review state.

This is intended architecture only; none of this service pipeline is implemented yet.

10. AI REASONING RULE
============================================================
PLANNED, NOT IMPLEMENTED: group all charges by Unit Id, retrieve the relevant evidence and requirements once for that unit, and make ONE AI call per unit containing all relevant charges plus that context. The AI response should contain an individual CLAIM, REJECT, or UNCERTAIN decision for each charge. Different Unit Ids receive separate calls. Missing or contradictory evidence should result in UNCERTAIN/review rather than an unsupported claim. No AI calls currently occur.

Example intended batching:
